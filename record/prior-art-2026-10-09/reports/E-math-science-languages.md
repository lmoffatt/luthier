### 2. Closest candidates

**SageMath categories + TestSuite.** This is the nearest working system to F1+F2 in a Python setting. A category carries its axioms. The associativity test is written once in `Semigroups.ParentMethods._test_associativity` and runs on every parent in any subcategory, over the elements that parent returns from `some_elements()`. It differs from Luthier in that the axiom is a class name, not a Bool predicate in the type. The tests are methods by convention, and nothing is recorded: no seed, no count, no certificate. Mechanism worth taking: the model (parent) supplies its own representative elements, and the theory's laws are inherited down the category hierarchy and run on them. For Luthier, that means a value of a theory could offer its own witnesses alongside the generator derived from the type.

**GAP properties, with CAP on top.** GAP stores what it knows about an object in the object's type. A property defines two sets, "known" and "known true", and the manual says a stored value can't be removed "because the system may have drawn conclusions from the old attribute value" (chap13 §13.5). That is close to F3's "membership is a certificate, nothing checked twice". The differences: GAP has no evidence grade, no hash and no persistence across sessions. CAP adds two things relevant to F5 and F6. The first is a derivation graph: each derived method declares which operations it uses and how many times, plus a weight, and `Saturate` settles each operation on its cheapest derivation (chap8 §8.2-2, §8.4). The second is input and output sanity checks with three levels, partial, full or disabled (chap1 §1.10). Mechanism worth taking: CAP's operation weight, computed from the weights of the operations a derivation uses times their multiplicity. Luthier would put measured costs where CAP uses static integers, and record the choice.

**GATlab.** It has the same object as Luthier's F1 (a theory is a signature plus laws, a model is a value) and adds theory morphisms that migrate models declaratively. It does not test axioms. The paper names "sample elements of the types in that model to check if the equations in the GAT actually hold" as a plan, not a feature (arXiv 2404.04837). Mechanism worth taking: model migration along theory morphisms, as the way to get Luthier's "one concept, several implementations" with a declared map between them.

**Bayesian statistical model checking.** This is the closest match to F8's statistical laws read in a Bayesian way. Input: a property P≥θ(φ), an acceptance threshold T ≥ 1, and a Beta(α,β) prior. Traces are sampled sequentially and the Bayes factor B is updated; the procedure stops when B > T or B < 1/T. The paper proves that the probability of a wrong answer can be made arbitrarily small. It is a model-checking algorithm, not a language feature, and the property sits outside any type. Mechanism worth taking: the conjugate Beta-Bernoulli sequential test as the default evidence engine for a sampled law, with α, β and T as the law's declared parameters. The certificate would then record the posterior, not just a pass. The method was applied to biological models (Jha et al., CMSB 2009); I didn't open that paper itself.

**Biocham 4.** Of the biology DSLs I looked at, this is the one closest to F15. A temporal-logic specification of behaviour gets a continuous satisfaction degree, the inverse of a violation degree, and that degree is used directly as the loss for fitting parameters. Formula robustness is used "with no extra cost" as the objective. It differs from Luthier in having no type, no certificate and no prior over the specification. Mechanism worth taking: define the discrepancy of a law as a violation degree, then turn it into a bounded satisfaction degree, so the same law serves both as a test (degree 1 or not) and as a loss.

**NumFuzz.** This is the only thing in the cluster that formalizes F7. Programs have an ideal real semantics and a floating-point semantics, and a graded monad in the types bounds the relative error between them, with soundness proved against both. Luthier instead checks real-valued laws on doubles with a tolerance given as a parameter. Mechanism worth taking: derive the tolerance a law is checked with from an error grade the type system computes, instead of guessing it. This matters for F13 (every criterion is a parameter): the parameter would get a computed default.

### 3. Features with nothing found in this cluster

- **F3 in full.** No content hash, no evidence grades, no chain graded by its weakest link, no persistence. GAP's stored properties are the only partial match.
- **F4.** Holes that block reduction until filled: only CAP's dummy implementations, which raise errors and don't block reduction.
- **F6.** Nothing marks an undescribed foreign function as debt. CAP's sanity checks are the nearest thing.
- **F10.** No provenance by hash inside a language. SED-ML/COMBINE describe experiments but, as far as I could check, don't pin inputs by hash (UNVERIFIED).
- **F11.** No minimal kernel executable by hand, and no interpreter stated in the language with the host certified against it.
- **F14.** Nothing designed for an AI writer and a human reader.
- **F15, the "use carries a prior and a cost" part.** Not found.

### 4. Surprises

- **Specware (Kestrel).** Outside this cluster, but close to F1. A spec is "a finite presentation of a theory" (signature plus axioms), and specification morphisms express both structure and refinement down to executable code. It is proof-oriented, with no testing. https://www.kestrel.edu/home/projects/specware/papers/specware/specware.pdf
- **The CAP authors' own triage.** On LocalCharts (May 2024), Mohamed Barakat describes CAP's policy. Core functions assume correctness, user-facing functions run quick incomplete checks, and a complete `IsWellDefined` check runs only when called explicitly. In the same thread, Owen Lynch (AlgebraicJulia) argues for correctness by construction. Both projects arrived at "check at a chosen level, not always", which is F13 applied to checking. https://localcharts.org/21521-inductively-correct-models-of-algebraic-theories.html
- **posteriordb.** One concept (a posterior), implementations in two languages, reference draws with documented validation. It is the closest existing practice to F5 for statistical code, though it is a database, not a language.
