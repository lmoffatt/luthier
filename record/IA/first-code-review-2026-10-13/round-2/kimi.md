## 2. The uniqueness argument of `ebnf.lth`

**Yes — on `WellFormedEbnf` the nine laws have exactly one solution, and I believe the argument.** The order is lexicographic: (i) a shorter token list; (ii) a structural subterm at the same list (`seq (a::rs)` calls `a` and `seq rs`; `alt`/`opt`/`rep` call their subterm); (iii) a ref-expansion at the same list (`RefUnion` replaces `ref n` by `rulesOf e n`), which is a DAG because `noneLeftRecursive` excludes cycles in `leftCalls`. Every recursive call in every law decreases in this order: `SeqSplits` at split `(nil, ts)` goes to the subterm `a` and the smaller `seq rs`; at `(xs, ys)` with both nonempty, to shorter lists; `RepRounds` at `(ts, nil)` hits the base `isEmpty ts`, and otherwise to strictly shorter lists since the first round must be nonempty. So no infinite descending chains, and each value is pinned by induction.

**The file's one-sentence statement of the order is slightly incomplete** — "values at a shorter list, or at the same list and a right-hand side reached without consuming" omits the structural-subterm clause, without which `SeqSplits` at the `(nil, ts)` split is not justified. The conclusion stands; the sentence should name the subterm case.

**`nullable`, `leftCalls`, `reachesLeft` compute what they claim, and `ruleCount` suffices.** A minimal empty derivation never repeats a nonterminal on a path, so depth `#productions ≥ #nonterminals` reaches the least fixed point of nullability exactly; longest simple left-call path ≤ `#nonterminals ≤ ruleCount`, so `reachesLeft e (ruleCount e)` explores enough. All three are total on any `Ebnf` (descent on `k` at refs, on structure elsewhere), so the predicate of `WellFormedEbnf` is computable on non-well-formed grammars too.

**The domain is right for this model, with two notes.** It excludes exactly what the backtracking recognizer cannot compute (any same-list recursion path traces a left-call cycle) — and it now *includes* nullable repetitions: `rep eps` is well-formed, and `RepRounds` pins it to `{[]}` while the model's `shorter` guard gives the same answer. That case broke everything in round 1; it is now inside the domain and determined. Slightly strict, deliberately: undefined nonterminals would actually be consistent (`RefUnion` pins them to false, the model agrees), so the `refsDefined` half is a lint, not a necessity; and grammars like `S ::= S | eps` are decidable in principle but excluded — defensible, since the domain of a certificate is the domain the model computes (L10.1).

## 3. `luthierSyntax`

**It is a `WellFormedEbnf`.** No production is left-recursive (the `term → … → atom` stratification descends; `negTerm`'s recursion is behind `lit "-"`; every other recursion is guarded or parenthesized), every referenced nonterminal is defined, and `"program"` is an `lhs`. Its coercion obligation is real and `test`-dischargeable.

**Faithful to chapter 2 as it now reads**, with three flags. (a) `and`, `or`, `mod`: chapter 2 still calls them "ordinary names written infix" (2.S2), but the file gives them token kind `"infix"` and `Op` constructors — so `and x y` as a prefix application, or any use of `mod` as an ordinary function, no longer parses. Either 2.S2 must drop "ordinary names", or the lexer should keep them as names and let the parser treat infix names by position. (b) The clause question (finding (2), see 6). (c) Chapter 2's 2.S9 atom list still physically contains `let`, `extern`, `forget` (marked retired / names of core); `luthierSyntax` omits them per the decisions. Consistent, but the productions should be removed from 2.S9, not annotated.

**No two-tree texts found.** I re-checked the old ambiguities: `{ a : Int | p }` derives only via `subtype` (the `record` production can never see a lone field); `{ a b : Int | a < b }` derives only via `record`; record-value vs block is decided by the trailing bare term; `recordFields`' two alternatives converge on one tree; `pattern`/`patom` overlaps (`x`, `_`) converge on one tree. One wrinkle, more 4 than 3: `patom`'s tuple allows a single pattern — `seq [lit "(", ref "pattern", rep …, lit ")"]` — while `subtypePattern`'s tuple requires two; so `(p)` is a text whose tree (`pTuple [p]`) `wellFormedPattern` rejects.

**`argAtom` does what 2.S10 asks**: a sum can head an application but not be its argument without parentheses, and `SumAsArgument` proves both directions. The split is a bit baroque (`atom` wraps `argAtom` plus the sum; `projTerm`/`argTerm` duplicate the dot-repetition) but sound.

## 4. The new laws of `grammar.lth`

**Wrong: none that I can disprove** — I checked every lexical, layout, precedence, and tree law against `luthierSyntax` and the constructors; the intricate ones (`OperatorContinuesLine` with `then`/`else` continuations, `RecordTree`'s two-field-many form, `SubtypeTree`'s three-way distinction, `BlockOrRecordValue` with `,`-separated rebindings) all hold.

**But `wellFormed` is not exactly the writable trees, in both directions, and this matters because it is the domain of `RoundTrip` and `ParsedIsWritten`:**

- *Admits trees no text gives*: `wellFormedAct (define …)` never checks the clauses — "`define x bs t b cs -> validName x and allBinders bs and maybeWellFormed t and wellFormedBody b`" — so a tree with an ill-formed clause body is in `WrittenProgram`, and a correct printer printing it yields an unparseable text, failing `RoundTrip` for a good model. And `operatorAct o t` accepts any `o`, but only `plus/minus/times/div` derive (`opSymbol`); `operatorAct eq` is unwritable yet admitted.
- *Rejects a tree some text gives*: `patom`'s single-pattern tuple means `match m { (p) -> … }` parses to `pTuple [p]`, which `wellFormedPattern` rejects (`atLeastTwo`). Either `patom`'s tuple must require two, or `wellFormedPattern` must admit one — and the two tuple productions should agree either way.

**Missing laws** (forms or rules with no law): clauses on a definition (production unsettled — finding (2)); `floatLit` and `stringLit` (no law mentions either — `NumberTokens`/`StringTokens` are lexer-level); `shapeParam` (no tree law uses it); a tree law for each remaining `Op` (`amp`, `orOp`, `andOp`, `eq`, `neq`, `plus`, `minus`, `div`, `gt`, `ge` — only `times`, `lt`, `le`, `arrow`, `modOp` are pinned as trees); a record *type* with trailing separator (`TrailingSeparators` covers record values, `match`, `data`, but not `{ a : Int, }`, which the production allows); `eval` as an application; `pWild` in a pattern.

Per 4.R3, the observer must be a law. Verdict per `data`:

- `Rhs` (ebnf.lth): all eight constructors observed by a law each (`EpsEmpty`…`RepRounds`) ✓.
- `TokenKind`, `Keyword`, `Op`: `kindName`/`keywordText`/`opText` plus injectivity laws and the lexical laws (`KeywordsLexAsKeywords`, `InfixNames`) — every constructor told apart ✓. (Note `j == k` on these *non-recursive* data relies on `==` on data; see the spec flag in 7.)

- **Told apart by nothing**: `Literal`'s three constructors — there is no observer function and no law mentions `floatLit` or `stringLit` at all (`intLit` only via `numeral`); `shapeParam` (no law); `pWild` (no law); and `pLit` appears only inside `wellFormedPattern`, which is a definition, not a law. These are exactly what 4.R3 calls "a constructor no observer distinguishes" — each needs one law (e.g. `parsesX "x := 3.5" (literal (floatLit 3.5))`, `parsesX "x := \"a\"" (literal (stringLit "a"))`, a `match` with a `_` arm and a literal arm, and a `\ (x, y) { … }` law).

## 6. The two new findings

**(1) `import` and `as` as keywords — agreed, and the specification should say so.** The import line binds names, which no function can do (D-2026-10-13-n), and if `import` remained a name, `import "x.lut" A` would also derive as a datum — the line would be genuinely ambiguous, as would `… as LA` as an application. Reserving them is the minimal fix. I would have 2.S21 add them to the keyword list explicitly ("`W`, `data`, `match`, `if`, `then`, `else`, `U`, `operator`, `quote`, `import`, `as`"), with one line of reason, and state the consequence: like the other keywords they are reserved everywhere, so no variable or field may be named `import` or `as`. The file marks this as a question for the specification; the specification must now answer it.

**(2) 2.S5's clauses — agreed, and the production should change, not the prose.** The prose says "Clauses under a header with parameters are a `match` on the tuple of the parameters" (2.S5) and 2.S12 translates them — but nothing states what a `body` *means* when clauses also follow it, and a clauses-only header does not derive. I would have 2.S5 say: `definition ::= name { binder } [ ":" term ] ":=" (body | clause { clause })` — a definition is either a plain body or clauses only; add a `clausesBody : List Clause -> Body` constructor (or make the body optional in the tree); add the 2.S12 row ("`f` with clauses is the `match` of the clauses on the tuple of the parameters"); and pin it with a tree law. The file is right to keep clauses unpinned until this is settled.

## 7. Syntax of the files

Under chapter 2 as it now reads — including the proposals chapter 2 carries — **no line fails to parse**, and I checked the risky ones: the multiline `&`-conjunctions (leading infix operator continues the item, 2.S4), the trailing `;` after `kwAs` and after the last `subtypePattern` branch (now allowed by D-2026-10-13-o), the trailing comma in `Grammar`'s record type, `(from to : String)` and `(a b : Rhs)` multi-name binders, the single-field record values and multi-name imports, and `(k - 1)` on `Nat`. Two dependencies to name: every string containing `\"`, `\\`, or `\n` (in `ImportTree`, `StringTokens`, the layout laws, `lit "\\"`) parses only under the escape proposal now marked in 2.S1 — if that proposal is not taken, those lines still lex but mean something else; and the import lines use 12.S22's form, which today's parser cannot read (the spec admits this).

**Disagreement with the specification itself, as a separate item**: 4.R8 still says `==` is defined "on products, sums, **recursive `data`** and subtypes built from types that have it" — but D-2026-10-13-o made non-recursive `data` ordinary (3.R3), and the files now compare `j == k` on `Keyword`, `Op`, `TokenKind` (e.g. `KeywordTextInjective … or j == k`) and match on them. 4.R8 should say `data`, or the new `data`s have no equality and both the injectivity laws and `ParsesWhatDerives`'s use of `derives` (a `Bool`-valued field) are unstatable.

## 8. What I would change first

**Make `wellFormedProgram` exactly the set of writable trees: check clauses in `define` and restrict `operatorAct` to the four bindable operators.** Reason: `WrittenProgram` is the quantification domain of the theory's two flagship laws — "`RoundTrip (d : Derives) (g : Grammar d) (p : WrittenProgram)`" and `ParsedIsWritten` — and a domain that contains unwritable trees breaks them in practice: a correct printer confronted with `operatorAct eq …` or a junk clause prints a text that does not parse, and `RoundTrip` fails a model that is right on every real tree. Until the domain is exact, "the parser gives no tree outside the domain of `RoundTrip`" is not true, and the other fixes — observers for `floatLit`/`stringLit`, the clause production, the `(p)` wrinkle — all hang off the same predicate being right.
