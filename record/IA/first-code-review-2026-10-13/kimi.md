## 1. Conformance to the specification

**Contradictions (the checker's rules it would reject):**

- `grammar.lth` defines four non-recursive `data` types: `TokenKind : U := data { nameToken : TokenKind ; … }`, `Keyword : U := data { kwData : Keyword ; … }`, `Op : U := data { amp : Op ; … }`, `Literal : U := data { intLit : Int -> Literal ; … }`. Chapter 3: "**A `data` definition has at least one constructor that mentions the structure being defined**" (3.R3), and 4.R4 rejects a non-recursive `data`: "write `x = t` (an alias, 4.R7)". These four must be aliases (`TokenKind = < nameToken : Unit | … >`) or theories.
- `ebnf.lth` and `grammar.lth` put plain definitions in theory files: `append`, `rulesOf`, `withStart`, `splits`, `prefixed`, `anySplit`, `anyRhs` (and `tokenView`, `kindName`, `opText` in grammar.lth). 12.S23: "**A theory file, extension `.lth`, holds types, declarations and laws**." A definition is none of the three. This is unmarked; either 12.S23 must allow "the vocabulary the laws use", or the helpers belong in a shared `.lut`.
- `datum : Surface -> SurfaceAct` contradicts 2.S5 (`act ::= declaration | definition | alias | directive`). The header justifies it by "D9 of the *superseded* plan" — that is not a decision id in force, and nothing marks the constructor itself `proposed`.
- Missing from `Surface`/`SurfaceAct` while chapter 2 has them: `eval` (2.S20: `"eval" term term` — only `quote` was kept), `profile` (2.S19: `act ::= … | "profile" name ":=" …`), and `let` (2.S9, still `[implemented]`; 2.S21 demotes it but "the parser reads the older forms today", so its absence should be marked, not silent).
- `luthierSyntax`'s `body` production — `"data", "{", opt (seq [cat "name", lit ":", ref "term", rep (seq [lit ";", …])]), "}"` — has no trailing `;`; 2.S5 allows `[ ";" ]` after each constructor. Same for `match` arms (2.S9 allows `[ ";" ]` per arm).
- `field ::= seq [cat "name", rep (cat "name"), lit ":", ref "term"]` derives `{ x y : A }`, but the tree `record : List (String * Surface) -> Surface` cannot represent one field with two names. The extra names have nowhere to go.
- `program ::= rep (seq [ref "act", lit "\n"])` forces every act, including the last, to be followed by "\n". 2.S5 is `program ::= { act }`. Nothing in the file converts `endToken` into a final "\n" — `endToken` is dead in `kindName … -> "end"` and unused in any production.
- 2.S1 defines four token kinds ("A name, a number, a string and a comment are"); `TokenKind` adds `symbolToken`, `newlineToken`, `endToken` without marking them. (Needed for layout, but unmarked.)

**Unmarked additions:** `LexError`/`ParseError` shapes (fine, but the plural `List ParseError` in `ParseResult` is a choice); splitting literals into `intLit`/`floatLit` is attributed to 2.S1, which says nothing about it; making `layout` a separate observable function of `Grammar` is sensible but is a design addition beyond 2.S4's prose.

**Disagreements with the specification itself (flagged separately, as instructed):** the import form. `grammar.lth` states 12.S22's `import "x.lut" N : T as M`, which contradicts chapter 2's 2.S6 (`"import" string [ "as" name ]`). The file is *right* — 12.S22 is the later decision (D-2026-10-13-n) — and chapter 2 is stale: 2.S6 now literally reads "The directives other than `test` are: Replaced: 2.S21.", i.e., the replacement text was lost. Chapter 2 must be repaired; the file should note the conflict. Also, chapter 2 vs itself: 2.S9 keeps `let` `[implemented]` while 2.S21 retires it; the files follow 2.S21 but the spec needs to say which stands.

## 2. Conformance to the principles

The 4.R10/L9.2 sin of draft 0 is genuinely fixed in shape: `derives` is declared in `ebnf.lth` ("`derives : Ebnf -> List TokenView -> Bool`", a hole) and given a body only in `ebnf_model.lut` ("`derives := \ (e : Ebnf) (ts : List TokenView) { hasEmpty (remainders e (ref e.start) ts) }`"). Same for the `Codec` pattern with `Grammar`. L14 is honored: the grammar is stated in Luthier, with the translation table of 2.S12 explicitly deferred to `term.lth` (acknowledged, not silent).

But: **the laws do not yet determine `derives`, and worse, as quantified they have no model at all** (see 3). So something still depends on the implementation: the model in `ebnf_model.lut` carries the least-fixed-point reading of `rep` and the totality the laws don't state. `Grammar`'s laws are in better shape — `RoundTrip`, `Canonical`, `ParsesWhatDerives` pin `parse ∘ print` and `accepts = derives`, which is what a second implementation (the Python parser, L14.3) needs to certify against.

## 3. The laws of `ebnf.lth`

**Not complete.** Ten laws pin `derives (withStart e r)` for every rhs form by structural recursion — except `rep`. `RepUnfolds` only states `rep a ≡ alt [eps, seq [a, rep a]]`, and that equation admits non-least solutions. Concrete counterexample: take `b → eps` (so `derives … b` is pinned to `{[]}`) and `start → rep b`. Any model with `derives (withStart e (rep b)) ts = true` for **all** `ts` satisfies the equation (RHS = `ts == nil ∨ derives … (rep b) ts`) and no other law mentions `rep`. Two models satisfy all ten laws and disagree. The file's comment ("`RepUnfolds` makes `derives` the least fixed point only together with termination") concedes a version of this; a leastness law is statable in the theory (e.g., an `unfolds : Rhs -> Nat -> Rhs` helper and a law `derives (withStart e (rep a)) ts == anyN … (derives (withStart e (unfolds a n)) ts)`), it just isn't.

**Inconsistent as quantified, and `withStart` is the cause.** It claims freshness it doesn't have: `{ start := "'start", rules := cons { lhs := "'start", rhs := r } e.rules }`. Every law quantifies over *all* `e : Ebnf`. If `e` contains a nonterminal named `'start`, the injected rule is added to the old ones, and the laws contradict: e.g. `LitOne` instantiated at a grammar whose old `'start` derives `"x"` forces `derives (withStart e (lit "a")) "x"` to be both true (via the old rule, through `RefUnion`) and false (via `LitOne`). Same poison in the law itself: `RefUnion` says `derives (withStart e (ref n)) ts == anyRhs e (rulesOf e n) ts` — for `n = "'start"` the RHS reads the *original* `e`'s rules and drops the injected rule. So as written the theory has no model; the quantification must be restricted (laws over a subtype `{ e : Ebnf | "'start"-free e }`, and `n ≠ "'start"`), since strings give no way to generate a fresh name.

**Redundant:** `StartIsRef` follows from `RefUnion` (given freshness): instantiate `RefUnion` at `n := e.start` and you get `derives e ts == anyRhs e (rulesOf e e.start) ts`. `OptIsAlt` is a definition, not a characterization — acceptable, but it is doing different work from the others. Otherwise the laws are individually right; I verified the model satisfies each (see 7).

## 4. The laws of `grammar.lth`

**Case laws: none is wrong.** I checked each pair against `luthierSyntax` and the tree constructors; the risky ones hold: `ArrowIsOneToken` (`a<-1` lexes name/arrow/number; `a < -1` is `binop lt a (neg 1)` with or without parens, since `negTerm` sits above `appTerm`), `NegationLooserThanApplication`, `DanglingElse` (the inner `ifThen` consumes the `else` through the `opt` at `term` level), `UnionAsArgument`, `BlockOrRecord` (a trailing bare term forces `block`; `{ a := 1 }` cannot mimic it since `recordValue` requires `:=` on every field), `NoArrowAtTopLevel` (`x <- 1` matches no act), `ImportNamesWhatEnters`. Two complaints: `ErrorsHaveLines`/`BrokenTextFails` are nearly vacuous, and several laws (`CommentDropped`, `KeywordsReserved`, all layout laws) depend on the lexer's and layout's behavior, which no law pins down — the suite could pass a wrong lexer.

**Chapter 2 rules with no law:** 2.S5 binders and defaults (`(x : A <- d)` — production present, no case law); clauses `| p, q := t`; 2.S6 `operator`; 2.S10 patterns (constructor vs label vs variable); 2.S14 dotted-name resolution; 2.S16 implicit binders `{A B : U}`; `sigmaNamed`/`sumNamed`; `mod` as infix name; number/string literal spellings; EOF/trailing-newline handling. The translation table of 2.S12 is deferred to `term.lth` — acknowledged in the header, acceptable.

**`luthierSyntax` faithfulness:** gaps as listed in 1 (missing `eval`/`profile`, trailing separators, `field` multi-name, `datum`, trailing newline). It is free of left recursion — I checked every production's leftmost symbol; all recursion is guarded (`negTerm` consumes `-` before recurring; `term` recurs only inside `( … )`). One genuine ambiguity the laws don't resolve: `{ x : A | p }` derives through both the record production (`opt (seq [lit "|", ref "term"])`) and the subtype production — the recognizer accepts, but no law says when the tree is `recordLaw` and when `subtype`, and a context-free parser cannot decide. (This is the strongest argument for merging the two constructors; see 5.)

## 5. The surface tree

**Completeness:** missing `eval` (2.S20), the `profile` act (2.S19), and `let` (if 2.S9 rather than 2.S21 is in force). Everything else of 2.S9 maps, including `W` (`world`) and `quote`.

**Two constructors that should be one:** `pName`/`pCon` (a bare name is `pCon` with an empty argument list — spec 2.S9 has a single production `name { patom }`); and `record`/`recordLaw` — a labeled base with a law is just the record plus the subtype overlay, and merging them kills the `{ x : A | p }` ambiguity of 4. Keep `sigma`/`sigmaNamed` (different binder structure, both in 2.S9).

**Positions:** don't carry them. The case laws compare trees with `==` (4.R8 structural), and `BlockOrRecord` builds expected trees literally; a position field would break every such law. Positions already live where they belong — in `Token` and `ParseError`. `RoundTrip` survives precisely because print is canonical and the laws only require `parse ∘ print = id` and re-parse stability (`Canonical`), which tolerate a non-injective printer. If positions were ever needed in the tree, they'd have to be a wrapper constructor with tree equality defined to ignore it — a complication with no payoff here.

## 6. Syntax of the files themselves

Under the syntax as *decided* (2.S21 keywords, 12.S22 imports, the file's own marked proposals), I found **no line that fails to parse**. Worth noting:

- The import lines — `import "ebnf.lth" Ebnf Rhs TokenView derives rulesOf append eps lit cat ref seq alt opt rep` — are correct per 12.S22 but today's parser (2.S6's old form) cannot read them; the spec concedes this ("The parser reads the older forms today"). Nothing can check any of it yet regardless.
- The layout laws use `\n` inside strings (`g.parse "f := {\n  a := 1\n…"`). As chapter 2 stands, a string is raw characters, so `"\n"` is backslash-n and the laws assert something other than intended; they silently depend on the marked-proposed escape rule. Same for `lit "\\"` in the lambda production (one backslash only under the proposal).
- The multiline conjunction `derives := EpsEmpty & … SeqSplits\n  & AltUnion …` parses only because 2.S4 lets a line beginning with an infix operator continue the item — fine, but it means these files already exercise the layout rule they state.

## 7. The model file

I verified `ebnf_model.lut` against each law on terminating, `'start`-free inputs: `EpsEmpty`, `LitOne`, `CatOne`, `RefUnion`, `AltUnion`, `OptIsAlt` hold directly; `SeqSplits` holds because `splits` enumerates exactly the contiguous partitions and the model's threading of remainders computes the same existential; `RepUnfolds` holds because both sides are the set `{ts} ∪ {≥1 consuming iterations}`. The `shorter` guard makes `rep` of an empty-matching body terminate, so divergence is exactly left-recursive nonterminal cycles (`ref n` expands without consuming first; e.g. `start → seq [start, lit "x"]`).

The divergence is **not** acceptable as the file frames it. The comment claims "a model that diverges on a left-recursive grammar does not fail these laws, it fails to answer (3.S11, fuel)". With fuel it *does* answer — it answers `false` — and the laws can force the opposite. Example: `start → seq [start, lit "x"] | eps`. `EpsEmpty` pins `nil`; then `SeqSplits` forces `"x"`, then `"xx"`, and so on — the equations have the unique solution "all finite strings of x", which the fuel-capped model (partial results = no remainders = `false`) denies. So on left-recursive grammars with terminating equation-sets, the model violates the theory it is meant to be certified against. A sampling certifier saves this only if (a) the laws are restricted to a well-formedness subtype (no `'start`, no left recursion) and (b) the generator draws adversarial rhs — empty-matching `rep` bodies in particular, which is exactly where a non-least model diverges from the intended one and where the current model is right.

## 8. What I would change first

**Restrict the quantification of the laws of `ebnf.lth` to `'start`-free grammars (and, in the same stroke, exclude left recursion).** Reason: as written the theory is *inconsistent* — no model satisfies all ten laws on all inputs — so every other question (completeness, the model's certification, the file's role as the pattern for later theories) is moot until the theory has a model. This is one subtype — `{ e : Ebnf | wellFormed e }` with `wellFormed` definable in the file — and it makes `withStart` honest. The very next change, because it is the reason the file exists (4.R10: a law characterizes), is the leastness law for `rep`; but inconsistency kills first, incompleteness second.
